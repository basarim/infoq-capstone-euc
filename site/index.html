01 The problem

The eval passes. The intent moved.

A prompt tweak, a model upgrade, a context-window change — any one of them can silently shift what an application does, while the tests, dashboards and stakeholders still assume the original intent holds. In deterministic software, a passing suite is a reliable proxy for correctness. In an LLM-reasoned system, behaviour can drift in ways that clear every superficial check and still fail the business goal.

It compounds because business intent itself is fragmented: partly in a requirements doc, partly in a prompt, partly in application logic, partly in ad hoc eval scripts. Each fragment changes independently. None of them is the source of truth, so when a model changes, teams often cannot say with confidence whether they are still building the same thing.

Fragment 01

Application logic

Encodes part of the intent in code that can at least be diffed — but only the part that was deterministic enough to write down.

Fragment 02

Prompt & context

Carries the judgement calls. Edited by whoever is closest to the model, on a cadence nobody else tracks.

Fragment 03

Evaluation criteria

Derived from intent once, informally, then maintained separately — so it drifts away from both of the others.

A passing eval shows internal consistency. It does not show that intent was preserved.
02 The artifact

One definition. Two consumers.

An Executable Use Case keeps the actor-and-goal framing that Ivar Jacobson gave the use case in 1992 — and replaces the prose flow with a machine-readable, ordered pipeline of typed stages that can actually run and actually be evaluated against. “Executable” is doing real work in the name, not branding.

The schema is shaped around pipe-and-filter. Each stage names a filter — a lookup key into a registry — so a pipeline is assembled mechanically from the definition rather than hand-wired per use case. A single deterministic check is a valid one-filter pipeline; a four-stage assessment is the same contract, larger.

context
The shared object that flows through the pipeline. seedFields names what exists before any filter runs; every stage declares what it reads and writes.
executionPipeline
An ordered, non-empty list of filter stages. Order matters — deterministic stages run before reasoned ones, so a cheap check can short-circuit an expensive model call.
policies
Cross-cutting constraints every reasoned stage must respect. Structurally an aspect: they belong to the use case, not to any one stage of it.
expectedOutcomes
The closed set of results the use case is allowed to produce.
evaluationPipeline
Scoring stages that read the same context execution wrote into — not a separately maintained copy of it.
grant-fit-assessment.json  ·  abbreviated
{
  "id": "grant-fit-assessment",
  "actor": "Nonprofit Program Manager",
  "goal": "Determine whether the organization should pursue a grant",
  "context": { "seedFields": ["organization", "grant"] },
  "executionPipeline": [
    {
      "id": "ELIGIBILITY-001",
      "filter": "eligibility",
      "type": "deterministic",
      "onFailure": "halt",          // contract, not convention
      "group": 1,
      "reads": ["organization", "grant"],
      "writes": ["eligible", "failedEligibilityRules"]
    },
    {
      "id": "ALIGNMENT-001",
      "filter": "alignmentReasoning",
      "type": "reasoned",
      "onFailure": "continue",
      "group": 4,
      "writes": ["fitClassification", "explanation",
                 "supportingEvidence", "identifiedUncertainty"]
    }
  ],
  "policies": ["Do not invent missing information", …],
  "expectedOutcomes": ["STRONG_FIT", "POSSIBLE_FIT", "POOR_FIT"],
  "evaluationPipeline": [ /* scored against the same context */ ]
}
03 The pipeline

Deterministic where it can be. Reasoned where it must be.

Stages execute in ascending group order, and the split is the point: three deterministic gates precede the one stage that needs a model to weigh evidence. That isolates exactly where EUC-driven evaluation earns its value — deterministic rules can be checked conventionally, but reasoning is the layer where a prompt or model change is most likely to drift silently.

1
ELIGIBILITY-001

Applicant must satisfy mandatory eligibility requirements.

deterministiconFailure: halt
2
GEOGRAPHY-001

Applicant must operate within the grant's specified geographic scope.

deterministiconFailure: halt
3
INFO-001

All required application information must be present before assessment.

deterministiconFailure: halt
4
ALIGNMENT-001

The organization's mission and programs are assessed for alignment with the funder's stated priorities.

reasonedonFailure: continue

The halt is a contract. A failed mandatory rule short-circuits straight to POOR_FIT without ever invoking the model — strong alignment cannot rescue a failed requirement. The schema says so; the runtime obeys it; a test proves the reasoner is never called after a halt.

Evaluation filter

eligibilityCorrectness

Scores all three deterministic gates against ground truth. Should stay perfectly stable when the model underneath changes.

Evaluation filter

programAlignment

Scores the reasoned classification against the expected outcome for the case.

Evaluation filter

evidenceGrounding

Checks that the conclusion is carried by evidence actually present in the context — not invented to fit.

Do not invent missing informationSupport conclusions with evidenceFlag uncertainty rather than defaulting to a confident conclusion
04 Measuring drift

Something has to stay still for movement to be measurable.

That is the whole wager. The EUC is the datum — fixed on purpose — while the prompt and the model underneath it are deliberately changed. If evaluation against that unchanged definition still catches the divergence, the artifact does its job. If behaviour drifts and the eval stays green, it does not, and that failure is the finding.

The EUC: unchanged across every variant Measured behaviour under prompt and model change

Drift detection rate

How often evaluation catches a change that genuinely altered behaviour.

False-flag rate

How often it raises drift when behaviour did not actually diverge.

Deterministic-rule stability

Whether the rule-based half stays perfectly stable, as it should.

Evidence-grounding consistency

Whether conclusions stay carried by evidence as the reasoning layer shifts.

05 Case study

Grant Fit Assessment.

Nonprofits fund programs partly by applying for grants, and applying costs real staff time — so they need to know in advance whether an opportunity is worth pursuing. The assessment compares an organization's profile and programs against a grant's requirements and priorities.

It makes a good testbed because eligibility and fit are not substitutes for each other. An organization can be eligible and still a poor fit; strong alignment cannot overcome a failed mandatory requirement. The two halves behave differently under evaluation, which is precisely what needs isolating.

Deterministic

  • Organization eligibility
  • Geographic requirements
  • Required information present
  • Mandatory constraints

LLM-reasoned

  • Mission alignment
  • Program alignment
  • Evidence interpretation
  • Explanation generation

Expected outcomes

STRONG_FITPOSSIBLE_FITPOOR_FIT

The eval dataset carries six cases with independently established ground truth, including the two that matter most — eligible but misaligned, and ineligible but aligned. Those are the cases where a drifting reasoner is most likely to give a plausible answer for the wrong reason.

06 Related work

Adjacent to spec-driven development. Aimed at a different failure.

Spec-driven development is fundamentally about generation — spec in, code out. Executable Use Cases are fundamentally about evaluation under drift: the definition does not change; the thing running underneath it does. These overlap, with different centres of gravity — not competing alternatives.

Spec-driven developmentExecutable Use Cases
DrivesGenerated code, tests, docsRuntime reasoning behaviour and evaluation criteria
ConsultedAt build time, before and during implementationContinuously — at every inference, not just at build
“Drift” meansCode diverging from the spec — a version-control problemThe model's judgement diverging from intent while the code is unchanged — a non-determinism problem
Over its lifeThe spec is updated when requirements change; code is regeneratedThe EUC stays fixed on purpose while the model and prompt beneath it change
07 Where this stands

A working prototype, and one honest gap.

Built

EUC schema and JSON authored; model and loader in Java, with validate() enforcing the pipeline contract at load time.

Built

Both halves are schema-driven: PipelineBuilder and EvaluationPipelineBuilder assemble their chains from the EUC through filter registries, with no per-use-case orchestration code.

Built

Deterministic eligibility engine and EUC-bound evaluator, both unit tested. The halt contract is verified offline with a reasoner that fails the test if it is ever invoked after a halt.

Built

Drift-experiment harness: baseline plus prompt and model variants, computing all four metrics — verified against known inputs with fake reasoners.

Pending

The first live eval pass and drift run against a real model. Every layer of wiring is verified offline; only the network call itself remains unexercised in this environment.

Evaluation needs a reference point that survives iteration — authored once, by the people who own the intent.

The contribution is not the grant application. It is a domain-independent pattern, and a falsifiable claim about it: that a fixed, machine-readable definition of intent can still tell you whether behaviour stayed correct after the model underneath changed. The proposal states what would disprove it.
